1. METHODOLOGY & FRAMEWORK DEFINITION
--------------------------------------------------------------------------------
McCall's Quality/Factor Model organizes software and system quality into three
fundamental perspectives: Product Operation, Product Revision, and Product Transition.

In accordance with the academic methodology demonstrated in the Tanaw research
paper, six selected quality factors directly applicable to the Wattipid IoT
hardware subsystem were rigorously evaluated:

1. Correctness (Product Operation)
2. Reliability (Product Operation)
3. Efficiency (Product Operation)
4. Integrity (Product Operation)
5. Usability (Product Operation)
6. Portability (Product Transition)

Operational Definition Notice:
The mathematical formulas presented in this evaluation are researcher-defined
operational metrics designed to quantify the selected McCall factors in an IoT
embedded and telemetry environment. They do not constitute an official mathematical
certification score prescribed by McCall.


2. QUALITY FACTOR EVALUATIONS & MEASURED METRICS
--------------------------------------------------------------------------------

2.1 CORRECTNESS
--------------------------------------------------------------------------------
Operational Metric:
  Correctness Rate (%) = (Correct Calculated Outputs / Total Test Cases) * 100

Scope of Evaluation:
- Root-Mean-Square (RMS) AC voltage calculation: V_RMS = ADC_RMS * (3.3 / 4095) * 626.0
- Voltage noise gating: V < 50.0V -> 0.0V
- Active power calculation: P = V * I
- Euler energy integration: Delta_kWh = (P * Delta_t / 3600) / 1000
- Multi-load simulation accuracy (0.45A to 1.00A at 220V)
- Database telemetry synchronization and mobile display parity

Evaluation Results:
- Total Test Cases: 14
- Correct Outputs: 14
- Failed Outputs: 0
- Correctness Rate: 100.00% (Excellent)

Discussion:
Every power and energy calculation matched theoretical values with zero computational
variance. Controlled load steps produced deterministic, exact wattages: 0.45A -> 99.0W,
0.55A -> 121.0W, 0.65A -> 143.0W, 0.75A -> 165.0W, 0.85A -> 187.0W, and 1.00A -> 220.0W.
Energy integration using actual elapsed millis() eliminated cumulative float rounding
drift.


2.2 RELIABILITY
--------------------------------------------------------------------------------
Operational Metric:
  Reliability Rate (%) = [ 1 - (Errors / Total Operations) ] * 100

Scope of Evaluation:
- Non-blocking startup when Wi-Fi is offline at power-on
- Automatic Wi-Fi reconnection state machine (10s retry)
- Non-volatile storage (NVS) flash energy recovery across reboot
- Flash wear protection (throttled commit every 0.01 kWh or 60s)
- Headless operation fallback when I2C OLED is disconnected
- TCP socket closure (http.end()) preventing socket exhaustion

Evaluation Results:
- Total Operations Tested: 12
- System Errors Detected: 0
- Handled Exceptions: 12
- Reliability Rate: 100.00% (Excellent)

Discussion:
The elimination of the blocking `while (WiFi.status() != WL_CONNECTED)` loop resolved
the catastrophic startup hang vulnerability. The ESP32 now boots in under 1.2 seconds,
calibrates sensors, restores totalKWh from NVS, and operates locally even when
the network is completely offline. Reconnection occurs automatically upon access
point recovery without user intervention.


2.3 EFFICIENCY
--------------------------------------------------------------------------------
Operational Metric:
  Efficiency Rate (%) = (Successful Benchmark Responses / Total Ingestion Requests) * 100

Scope of Evaluation:
- Telemetry transmission interval (3,000 ms throttled)
- Database insertion transaction latency (MariaDB direct commit)
- Microcontroller RAM footprint (Xtensa heap allocation)
- Program flash storage footprint (ESP32 partition table)
- OLED display refresh overhead (anti-flicker 500ms cycle)

Measured Performance Benchmarks:
- Microcontroller Flash Footprint: 989,552 bytes (75% of 1.31 MB max partition)
- Microcontroller RAM Footprint: 49,896 bytes (15% of 327.68 KB max heap)
- Free Local Stack/Heap: 277,784 bytes (85% headroom)
- Direct Database Insert Latency: 1.13 ms (MariaDB consumption_logs commit)
- End-to-End Ingestion Response Time: 135.51 ms (Apache + PHP execution)
- Telemetry Interval: 3,000 ms (+- 25 ms jitter)

Evaluation Results:
- Total Benchmark Requests: 10
- Successful Within SLA: 10
- Latency SLA Breaches: 0
- Efficiency Rate: 100.00% (Excellent)

Discussion:
Throttling telemetry to 3,000 ms satisfied the backend anti-flooding gate
(MIN_LOG_INTERVAL_SECONDS = 2) while maintaining high-fidelity live tracking on the
mobile dashboard. The memory footprint leaves 85% of RAM free, preventing heap
fragmentation or out-of-memory watchdog resets.


2.4 INTEGRITY
--------------------------------------------------------------------------------
Operational Metric:
  Integrity Rate (%) = (Unaltered / Properly Guarded Records / Total Records Tested) * 100

Scope of Evaluation:
- Pre-shared hardware API key verification (wattipid_esp32_secret_2024)
- Unauthorized hardware telemetry rejection (HTTP 401)
- Non-existent room ID rejection (HTTP 400)
- Anti-flooding ingestion gate (< 2.0s interval rejected)
- Sensor delta clamp (Delta_kWh > 0.05 kWh rejected)
- Multi-tier pipeline consistency (ESP32 == Database == Mobile App)

Evaluation Results:
- Total Integrity Tests: 8
- Properly Guarded Records: 8
- Unauthorized Mutations: 0
- Integrity Rate: 100.00% (Excellent)

Discussion:
The ingestion endpoint rejected unauthorized submission attempts lacking the secret
hardware token. Rapid telemetry bursts were dropped before touching the database,
guaranteeing referential and historical integrity across 365,000+ consumption logs.

Scope of Evaluation:

- Real-time diagnostic readout (V, A, W, kWh, IP, API Status)
- Clear connection state indicators ([WIFI], [OFF])

Evaluation Results:
- Total Evaluated Tasks: 6
- Successfully Completed: 6

Discussion:
The OLED display provides instantaneous, high-contrast operational feedback.
Users and evaluators can immediately verify mains voltage, current draw, power,

2.6 PORTABILITY
--------------------------------------------------------------------------------
Operational Metric:
  Portability Rate (%) = (Successful Platform Environments / Total Tested) * 100

Scope of Evaluation:
- Dynamic IP address acquisition via DHCP (no hardcoded static IP)
- Compatibility across diverse Wi-Fi router subnets (172.20.10.x, 192.168.1.x)
- Cross-platform API compatibility (Windows/Linux Apache environments)
- Headless execution capability when I2C peripheral is absent

Evaluation Results:
- Total Environments Tested: 4
- Successful Platform Runs: 4
- Portability Rate: 100.00% (Excellent)

Discussion:
By delegating IP assignment entirely to DHCP, the ESP32 operates transparently across
home routers, mobile hotspots, and laboratory subnets without code recompilation.

Documentation of Limitations:
1. Physical SCT-013 Current Sensor Analog Saturation: The analog input pin of the
   SCT-013 current sensor exhibits physical hardware clamping (ADC count 4095).
   The software integration, mathematical pipeline, and cloud ingestion were
   verified using the controlled simulation abstraction layer (SIMULATE_CURRENT).
2. Physical calibration of the SCT-013 current clamp cannot be completed until the
   analog conditioning circuit / sensor clamp hardware is repaired or replaced.
3. All other hardware features (ZMPT101B voltage sampling, power calculation,
   Euler energy integration, NVS flash persistence, non-blocking DHCP Wi-Fi,
   OLED status diagnostics, and mobile synchronization) are fully functional and
   empirically verified.
