1. DEFICIENCIES IDENTIFIED IN PREVIOUS FIRMWARE IMPLEMENTATION
--------------------------------------------------------------------------------
A thorough static and dynamic audit of the original `esp32_monitor.ino` revealed
several critical architectural flaws, stability risks, and standard violations:

1. Infinite Blocking Wi-Fi Loop in `setup()`:
   - Original code contained: `while (WiFi.status() != WL_CONNECTED) { delay(500); }`
   - Problem: If the Wi-Fi router was powered off or out of range at boot time, the
     ESP32 hung indefinitely in `setup()`. Sensors were never calibrated, NVS energy
     was never loaded, OLED froze on "Connecting WiFi...", and the local monitoring
     loop never executed.

2. Unstructured, Ad-Hoc Current Simulation Logic:
   - Original code had raw `random(120, 146)` simulation logic directly embedded in
     `loop()`, mixing measurement, simulation, and presentation logic into a single
     monolithic block.
   - Problem: Prevented clean transition to physical sensor operation when the
     SCT-013 is repaired, and lacked deterministic stepped loads for thesis validation.

3. OLED Display Over-Refresh & Severe Screen Flickering:
   - Original code called `display.clearDisplay()` and `display.display()` on every
     iteration of `loop()` (~10 to 50 ms).
   - Problem: Flooded the I2C bus with display commands, created visible screen
     flickering, and consumed unnecessary CPU cycles.

4. Lack of HTTP Timeout in Telemetry Transmission:
   - Original `HTTPClient` did not specify an explicit timeout (`http.setTimeout()`).
   - Problem: If the PHP backend hung or the network dropped packets during transmission,
     the ESP32 blocked for the default 5,000 ms timeout, causing severe hiccups in
     local energy accumulation.

5. Unchecked API Response Status:
   - Original code only printed the raw HTTP response code to Serial without checking
     the JSON response body or tracking connection state.
   - Problem: Failed to detect backend throttling (`skipped: true`), JSON syntax errors,
     or API authentication rejections, giving false confidence in telemetry success.

6. Missing Headless Peripheral Fallback:
   - If the SSD1306 OLED failed to initialize on I2C address 0x3C, the code continued
     calling display methods indiscriminately.


2. TECHNICAL ARCHITECTURAL IMPROVEMENTS & FIXES IMPLEMENTED
--------------------------------------------------------------------------------

Fix 1: Non-Blocking Startup Sequence & Wi-Fi Handshake
  - Replaced the infinite `while` loop in `setup()` with a bounded 4-second connection
    attempt. If connection is not established within 4 seconds, the ESP32 logs:
    `[WIFI] Initial connection timed out. Proceeding to offline measurement mode.`
  - The setup continues to initialize sensors, restore cumulative energy from NVS,
    and begin local electrical monitoring immediately.

Fix 2: Clean Sensor Measurement Abstraction Layer
  - Established a modular functional abstraction:
    * `float readVoltageRMS()`: Discrete 300-sample RMS integration over 60 ms
      with DC bias offset subtraction, noise gate (< 50V -> 0V), and over-voltage
      clamp (> 300V -> 300V).
    * `float readCurrent(float voltage)`: Modular abstraction supporting physical
      analog reading via EmonLib on pin 35 or controlled simulation inputs.
    * `float calculatePower(float voltage, float current)`: Pure mathematical function
      P = V * I with zero-voltage/zero-current short-circuiting.
    * `float calculateEnergyDelta(float powerWatts, float elapsedSeconds)`: Deterministic
      Euler integration: Delta_kWh = (P * dt / 3600) / 1000.

Fix 3: Controlled Step Load Simulation (SCT-013 Defect Isolation)
  - Implemented `#define SIMULATE_CURRENT true` with standardized test loads:
    0.45A (99W), 0.55A (121W), 0.65A (143W), 0.75A (165W), 0.85A (187W), and 1.00A (220W).
  - Automatically steps through test loads every 15 seconds when AC voltage is present.
  - Automatically drops to 0.00A when voltage drops below 50V (simulating device unplugged).
  - Serial output explicitly logs `[SIMULATED]` for scientific transparency.
  - Setting `SIMULATE_CURRENT false` immediately restores real ADC sampling on CT_PIN.

Fix 4: Non-Volatile Energy Persistence (NVS via Preferences.h)
  - Cumulative billing energy (`totalKWh`) is restored from NVS on cold boot.
  - Flash Wear Protection: Commits to NVS only when:
    * Cumulative energy delta >= 0.01 kWh, OR
    * 60 seconds have elapsed and energy has changed.
  - Preserves flash endurance for 10+ years while guaranteeing billing continuity
    across power outages.

Fix 5: Automatic Network Discovery (DHCP Zero-Configuration)
  - Configured `WiFi.mode(WIFI_STA)` with automatic DHCP IP acquisition.
  - Completely removed hardcoded static IP constraints, enabling plug-and-play
    mobility across residential Wi-Fi, lab subnets, and mobile hotspots.

Fix 6: Non-Blocking Wi-Fi Reconnection State Machine
  - Dedicated non-blocking routine `checkWifiConnection(now)` in `loop()`.
  - If `WiFi.status() != WL_CONNECTED`, triggers `WiFi.reconnect()` every 10 seconds.
  - Never freezes sensor sampling or local energy accumulation.

Fix 7: SSD1306 OLED Anti-Flicker & Rich Diagnostics
  - OLED refresh locked to 500 ms timer (`OLED_REFRESH_INTERVAL`).
  - Displays room ID, network state (`[WIFI]` / `[OFF]`), real-time V, A, W, kWh,
    DHCP IP address, and API connection status.
  - Graceful fallback: If OLED is not detected, `oledAvailable = false` and display
    calls are bypassed without crashing.

Fix 8: Resilient Telemetry Transmission & Anti-Flooding Compliance
  - Transmission interval set to 3,000 ms (`TELEMETRY_SEND_INTERVAL`).
  - Complies with backend `MIN_LOG_INTERVAL_SECONDS = 2.0s` anti-flooding gate.
  - Explicit HTTP timeout set to 2,500 ms (`http.setTimeout(2500)`).
  - Validates HTTP 200 response and deserializes JSON response body to detect
    throttling (`resDoc["skipped"] == true`) or success.
  - Strictly guarantees socket cleanup via `http.end()`.

Fix 9: Zero Relay Artifacts
  - Completely verified that no relay GPIOs, relay toggles, or relay documentation
    exist in the firmware, adhering strictly to the capstone submetering scope.

5. INSTRUCTIONS FOR HARDWARE FLASHING & OPERATION
--------------------------------------------------------------------------------
1. Connect the ESP32 DevKit V1 to your PC via a micro-USB data cable.
2. Open the Arduino IDE or execute via Arduino CLI:
   ```bash
   arduino-cli compile --fqbn esp32:esp32:esp32 hardware/esp32_monitor/esp32_monitor.ino
   arduino-cli upload -p COM_PORT --fqbn esp32:esp32:esp32 hardware/esp32_monitor/esp32_monitor.ino
   ```
3. Open the Serial Monitor at 115,200 baud.
4. Verify boot output:
   - OLED displays splash screen and room ID.
   - NVS restores cumulative energy.
   - Wi-Fi acquires DHCP IP address.
   - Telemetry begins streaming every 3 seconds to the Wattipid API.
5. In the Wattipid Mobile App, open the Tenant Dashboard for Room 1.
   - Live consumption card displays matching voltage, current, active power,
     cumulative energy, and `Device Online` status.
