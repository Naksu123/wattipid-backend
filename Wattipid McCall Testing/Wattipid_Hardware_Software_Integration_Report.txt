1. INTEGRATION ARCHITECTURE & DATA FLOW SPECIFICATION
--------------------------------------------------------------------------------
The hardware-to-software integration pipeline connects physical electrical monitoring
to tenant and landlord user interfaces through five rigorously decoupled layers:

Layer 1 — IoT Sensor Sampling (ESP32):
  - Samples AC voltage via ZMPT101B and acquires current via modular abstraction layer.
  - Computes instantaneous active power: P = V * I.
  - Integrates energy consumption over actual elapsed time: kWh = (P * dt / 3600) / 1000.
  - Commits cumulative energy to local non-volatile storage (NVS) to survive reboots.

Layer 2 — Network Communication & DHCP:
  - Connects to standard 2.4 GHz IEEE 802.11 b/g/n wireless access points.
  - Obtains network parameters (IP address, Subnet Mask, Gateway, DNS) automatically
    via Dynamic Host Configuration Protocol (DHCP).
  - Eliminates static IP requirements, enabling zero-configuration deployment across
    subnets (e.g., 172.20.10.x, 192.168.1.x).
  - Runs a non-blocking reconnection state machine checking link status every 10 seconds.

Layer 3 — Backend API Gateway (PHP 8.2 / Apache 2.4):
  - Ingestion Endpoint: POST /wattipid_backend/api.php
  - Enforces Hardware API Key verification ("wattipid_esp32_secret_2024").
  - Deep-sanitizes JSON payloads to prevent injection attacks.
  - Enforces an anti-flooding ingestion gate: rejects posts arriving with interval < 2.0s.
  - Clamps abnormal noise spikes (Delta_kWh > 0.05 kWh per reading clamped to 0).
  - Updates room activity timestamp (rooms.last_seen = NOW()).

Layer 4 — Database Transaction & Persistence (MariaDB 10.4):
  - Inserts telemetry rows into `consumption_logs` table (365,000+ existing records):
    (room_id, tenant_name, voltage, current_val, power, energy, energy_cumulative, cost, billing_cycle_id).
  - Associates telemetry with the active billing cycle for Room 1 (billing_cycle_id = 17).
  - Computes incremental cost based on current utility rate (PHP 12.50 / kWh).

Layer 5 — Mobile Application Synchronization (React Native / Expo SDK 52):
  - Mobile client polls `getLatestConsumption` authenticated via JWT token.
  - Determines device online/offline state: (time() - strtotime(last_seen)) < 30 seconds.
  - Renders real-time voltage, current, active power, cumulative energy, and power factor.

5. FAILURE-RECOVERY & RESILIENCE PROFILING
--------------------------------------------------------------------------------
A. API Server Temporary Outage:
   - Stimulus: HTTP POST sent while backend service is offline.
   - ESP32 Behavior: http.POST() returns negative error code (-1 / connection refused).
   - Recovery: The ESP32 does not crash, does not block the loop, releases the socket
     via http.end(), updates OLED to "API: Err -1", and continues local voltage and
     power measurement uninterrupted. Once the API returns, telemetry resumes automatically.

B. Wi-Fi Router Interruption:
   - Stimulus: Access point disconnected during operation.
   - ESP32 Behavior: WiFi.status() transitions from WL_CONNECTED to WL_DISCONNECTED.
   - Recovery: Telemetry transmission is bypassed, avoiding TCP timeouts. The non-blocking
     state machine attempts WiFi.reconnect() every 10 seconds. OLED reports "WiFi: Reconnecting...".
     When the access point returns, the connection is re-established in < 1.5 seconds.

C. Rapid Telemetry Flooding Defense:
   - Stimulus: Telemetry posts sent at 50ms intervals.
   - Backend Behavior: IoTService computes time difference from the previous log.
     Since timeDiff < 2.0s, the request returns {"success": true, "skipped": true}.
     Zero duplicate records are created in MariaDB.
